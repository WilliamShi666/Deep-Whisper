# Deep Whisper Personal 制作计划

状态：已批准并已公开发布；代码MIT已确认。2026-10-08补充：角色与壁纸适用CC BY-NC-SA4.0，独立品牌个人自托管授权已确认，见ASSETS.md；下列阶段表保留原计划记录。

## 1. 交付目标

把当前商业版副本制作成个人可自行运行的版本。新用户无需了解原项目商品、价格、商户、生产数据库、验证码或运营后台，只需要安装运行环境并配置自己要使用的 AI / 可选邮件服务。

目标流程是：clone → `pnpm install --frozen-lockfile` → 复制安全的 `.env.example` 为 `.env.local` → 填一把 DeepSeek key 或完整三把 key → `pnpm run doctor` → `pnpm dev` → 创建伴侣和开始聊天。数据库和媒体目录由程序首次初始化，后台任务由启动器一并启动。这些命令均须在实施阶段交付并通过干净 clone 验收。

## 2. 功能范围

| 当前功能 | 个人版处理 |
|---|---|
| 8 个身份、两种比例、捏人、多个伴侣/会话 | 保留；素材授权审核另设发布门槛 |
| SSE 聊天、开场白、人格完善 | 保留，去掉商业每日额度 |
| 用户发图、照片、云端语音和音色 | 保留；由功能配置决定是否可用，不由会员决定 |
| L1 画像、关系快照、长期记忆、偏好、遗忘 | 保留；存储与检索改成 SQLite |
| 40 张壁纸、色调、梦幻蓝/玫瑰、中英文 | 保留已有核心体验 |
| 主动来信、重要日期、停收/恢复 | 保留；站内收件箱作为默认投递渠道 |
| 邮箱注册、OAuth、验证码、匿名认领 | 用单主人身份替换；远程模式只提供单主人密码登录 |
| 会员、支付、价格、订单、退款、计费 webhook | 从开源运行时、页面、测试与配置模板移除 |
| 消息反馈 | 保留为个人记录；移除运营管理端及其独立令牌 |
| Vercel Cron、Resend 运营回执 | 默认换本地 worker；Resend adapter 可选 |
| 收外部邮箱邮件并自动聊天 | 首版不做；现有项目也没有该能力 |
| 团队、租户、协作、多个账号 | 不提供 |
| 全部 AI 在本机运行 | 不在首版；本地数据存储不等于离线 AI |
| 从商业生产库自动导入 | 不在默认交付中；以后提供用户授权的离线导入工具 |

## 3. 分阶段实施

各阶段完成代码后先合入本地集成分支，禁止把原生产目录当作测试环境。实施分支建议 `codex/deep-whisper-personal`，不自动 push。

| 阶段 | 工作与主要改动面 | 前置条件 / 交付证据 |
|---|---|---|
| P0 契约与技术验证 | 冻结核心 API/SSE/testid；Node 24 + better-sqlite3 + Drizzle + Next standalone 包装；FTS5 中文样例、SQLite 并发/备份、千问平台端点配对验证 | 新增隔离的技术验证测试；记录 native 安装与平台限制；live 验证另按 canary 门禁 |
| P1 配置与持久化基础 | 新安全模板、配置 schema、`pnpm run setup`、doctor、数据目录、SQLite schema/迁移、repository、版本检查、data:backup/data:migrate/test:sqlite脚本 | 空目录初始化、旧版本升级、回滚与恢复用真实临时 SQLite 验证 |
| P2 单主人与核心 CRUD | visitor/owner 适配、去 Supabase Auth、替换 SDK 查询、伴侣/会话/画像/主题/反馈；本机入口与远程密码模式 | 核心 route 合约、归属保护、同一 owner 重启/跨浏览器一致 |
| P3 去收费与媒体 | 删除 billing 页面/门禁/SDK/构建校验，解绑 Waffo PromptScan，保留内容安全和 provider contracts；私有本地媒体支持 production | 三-key 配置无会员可用；缺可选 key 的可读状态；生产 build/start 不需要商户或 R2 |
| P4 记忆与可靠任务 | FTS5 中文预分词/BM25、可选向量/RRF、无向量仍写记忆、快照 fencing、来源/遗忘、持久任务与 worker | 真实 SQLite 检索、删除、重启、失效竞争测试；既有记忆纯逻辑回归 |
| P5 来信与邮件 | 本地调度、站内来信、可选 SMTP/Resend、偏好与外发状态；无需注册邮箱即可站内收信 | 时钟驱动的日期/频控测试；本地假 SMTP 边界测试；重复/未知投递测试 |
| P6 开发者交付 | 重写 README/AGENTS/配置文档，Docker 与卷，CI，清理历史私有文档/资产/生产链接；许可证和依赖审计 | 三个平台干净 clone、容器重启、备份恢复；不存在私有域名/商户才能 build 的依赖 |
| P7 独立 review | 未参与对应实现的成员分别 code review、spec review；作者修复后复核 | 两份独立报告与编号需求追踪，P0/P1 问题归零 |
| P8 专职 E2E | review 通过之后，单独成员在干净检出和新数据目录跑完整浏览器流程 | E2E 报告、录屏/截图、环境键名清单；真实云能力另标验收边界 |
| P9 发布准备 | 生成候选 tag/变更说明、公开快启说明与发布清单 | 所有者确认许可证/素材权利和最终发布；本计划不授权 push/发布 |

P0/P1 是后续并行工作的共同底座；之后可以并行实现核心 UI/CRUD、记忆、邮件，但必须按约定的 repository/config/job contracts 工作。不要让几名成员同时重写 `runtime.ts`、schema 或共享响应类型。

## 4. TDD 的执行方式

1. 从 [Spec](03-spec.md) 选一组编号要求，先写会因为缺少产品行为而失败的测试，保存失败输出。
2. 实现足够使测试通过的真实业务逻辑；数据库层使用临时真实 SQLite，不把查询链全 mock。
3. 在绿色测试保护下整理代码，补失败、竞争、关闭与重启路径。
4. 每批记录需求编号、修改路径、Red/Green 命令、结果、剩余边界，再交独立 review。

mock 只放在网络/供应商、时钟、邮件 transport 等 IO 边界。FTS5、外键、事务、迁移、任务租约、快照竞争和文件写入不能靠返回固定成功的 mock 验收。默认测试使用生成的假内容，绝不载入现有 env、生产库或真实邮件地址。

## 5. 团队审查与验收顺序

- 实现成员：按子域执行 TDD；不得担任自己所写模块的最终 code reviewer。
- code reviewer：检查身份、事务、竞态、SQL、文件边界、配置、错误与 provider 策略，附源码定位和复现。
- spec reviewer：逐项检查 OSS 编号是否满足，识别只隐藏 UI、实际仍依赖商业资源的情况。
- E2E 成员：两种 review 完成并修复后再执行浏览器与快启验收；不得仅复述作者测试结果。
- 集成人员：汇总报告，确认修复未引起回归；新修改需重跑受影响检查，避免无理由重复全部测试。

拟定检查：`pnpm ts-check`、`pnpm lint:build`、`pnpm test:unit`、`pnpm test:providers`、`pnpm test:memory`、新增 `pnpm test:sqlite`、改造后的 `pnpm test:e2e`、`pnpm build`、`pnpm start`。其中新增/改造脚本不得冒充当前已可运行的脚本；旧 Supabase E2E 不直接沿用。

## 6. 完成定义

满足所有必须级 Spec；新用户只有一把 DeepSeek key 能开始真实聊天并持久保存关键词记忆，三把有效 key 能用核心图片/语音/语义记忆；不配邮件也能收到站内来信。正常重启与删除后，旧任务不能复活被遗忘记忆。恢复备份恢复到该备份时点，旧备份可能包含后来才删除的内容，不承诺跨历史备份永久删除。production build/start 与 Docker 都使用可持久化的本地目录。

必须把“离线 mock E2E 成功”“真实 provider 输出成功”“人工听到音色”“实际邮箱收到信”分别记录。供应商账号权限、区域、余额或模型停服不能靠 env 语法校验保证；不把 HTTP 200、SMTP accepted 或构建成功写成全功能已验收。

## 7. 风险与范围控制

最大工作量是解除遍布 route/后台任务的 Supabase 与会员耦合，而非安装 SQLite。其次是中文检索、记忆写入可靠性和后台信件。先完成底座与一条完整聊天路径，再扩展到其他领域。

当前复制的 Git 历史、docs/evidence/生产配置痕迹和素材需要单独整理。推荐从审过的文件清单创建干净公开仓库历史；不在本轮重写当前 `.git` 或删除现有证据。需要保留来源和上游授权声明。不会因为扫描未找到跟踪的 `.env` 就宣称整仓没有秘密。
